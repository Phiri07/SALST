# SALST deployment to Render + Neon

This is a separate deployment copy of the supplied SALST PWA.

## Before deployment
1. Rotate the Neon database password shared in chat and use the new connection string.
2. Verify `current.sql` imported the correct tables and records into Neon.
3. Do not commit secrets or `.env` files.

## Deploy
1. Create a private GitHub repository and upload the **contents of `SALST_PWA`** (so `render.yaml` is at the repository root).
2. In Render select **New > Blueprint** and connect the repository.
3. Supply `SALST_DATABASE_URL` with the new Neon direct connection string, including `sslmode=require`. `SALST_SESSION_SECRET` and `SALST_INGEST_KEY` are generated by Render.
4. Deploy. Render installs dependencies, runs the idempotent schema initializer and starts Gunicorn.
5. Open `https://<your-service>.onrender.com/api/health`, then the PWA. Test registration, login, tags and saved data.
6. Any existing ingestion client must use the same `SALST_INGEST_KEY` configured on Render.

## Limitations
- This Render web service does **not** run the four local Python simulator processes automatically. Local `./start.sh` still starts them.
- The PWA is a software demo. LR1121/E80 gateway bridge and ESP32 Wi-Fi telemetry are not integrated or tested.
- `/api/health` confirms the Flask app responds, not that PostgreSQL queries succeed. Test database-backed pages.
- Physical-tag emergency reset acknowledgements are not implemented.
- If database initialization fails, preserve Neon data and compare the imported schema before changing tables.
- Never run `./start.sh --reset-reports` against production Neon.

## Local use
Copy `backend/.env.example` to `backend/.env`, supply your local credentials, then run `./start.sh`.
